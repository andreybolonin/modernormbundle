# ModernORM: Composite PK → Surrogate PK Migration

**Статус:** контракт MVP / RFC будущих расширений

**Компонент:** ModernORM Bundle / `SchemaRekey`

**Команда:** `modernorm:data:transfer --schema-rekey`

Практическое руководство: [docs/schema-rekey.md](docs/schema-rekey.md).

**Основной сценарий:** полный перенос MySQL → PostgreSQL с преобразованием ключей

## 1. Цель

Предоставить управляемый механизм преобразования таблиц с составными первичными ключами (`composite PK`) в таблицы с одиночными суррогатными идентификаторами (`BIGINT` в MVP; UUID — отдельное будущее расширение), сохраняя данные, бизнес-уникальность и ссылочную целостность.

Это позволяет использовать legacy-схемы в ModernORM без обязательной поддержки составных PK у Entity в runtime. **Миграция схемы не гарантирует автоматическую совместимость прикладного кода:** SQL-запросы, ORM mapping, процедуры и внешние интеграции могут требовать изменений.

## 2. Область применения

### Поддерживаемый базовый сценарий

- Источник: MySQL; назначение: PostgreSQL.
- Таблицы Entity с составным PK из целочисленных колонок в MVP; расширение типов требует отдельного контракта сравнения.
- Создание нового одиночного PK и сохранение исходных ключевых колонок.
- Перенос через staging и переписывание **явно объявленных** FK на полный исходный PK.
- Ациклический граф зависимостей; преобразования задаются явно для каждой таблицы и FK.
- Целевая схема и ORM mapping подготовлены и проверены до запуска переноса.
- Старые ключевые колонки сохраняют `NOT NULL` и эквивалентный `UNIQUE`; различия сравнения значений должны быть проверены.
- Проверка полноты и корректности переноса до переключения приложения.

### За пределами MVP

- Автоматическое обнаружение неявных ссылок без FK.
- Полностью автоматическая адаптация прикладных SQL-запросов и сторонних интеграций.
- Произвольные циклические зависимости и сложные схемы без ручного плана.
- Resume, checkpoints, постоянные карты ID между запусками и CDC.
- UUID, ссылки на альтернативные составные `UNIQUE`, nullable составные FK и цепочки, где переписываемый FK входит в идентификатор зависимой Entity либо в ключ с входящими ссылками. Обычные join tables без входящих ссылок обрабатываются отдельно, как описано в разделе 6. Эти случаи явно блокируются на preflight.
- Автоматическое применение DDL финальной схемы, удаление старых колонок и автоматический cutover.
- Автоматическое преобразование всех особенностей MySQL (триггеров, процедур, коллаций и т. д.).

### Контракты выполнения

**MVP — offline transactional migration.** Запись в MySQL остановлена до открытия read-only snapshot и остаётся остановленной до завершения переключения. Команда не включает maintenance mode. Во время выполнения неизменность источника обеспечивается обязательным source fence, описанным в разделе 14.1; остановка приложения до запуска и сохранение запрета записи после выхода команды остаются обязанностью оператора. Приложение и workers не обращаются к целевым таблицам во время переноса.

Staging, назначение ID, преобразование FK, загрузка финальных таблиц и проверки выполняются в одной транзакции PostgreSQL. Commit допускается только после полной проверки. При ошибке выполняется rollback; повторный запуск начинает перенос заново с пустой целью. Стабильность новых ID между неуспешными попытками не гарантируется.

**Future — resumable migration.** Отдельный будущий контракт с checkpoints, постоянными ID mapping и определённым способом согласования прогресса с источником. Возможные основания: длительная остановка записи, неизменяемая копия источника либо snapshot вместе с CDC. Сохранённая карта ID сама по себе не обеспечивает безопасное возобновление. Этот контракт не реализуется в MVP.

## 3. Пример трансформации

Исходная таблица MySQL:

```sql
CREATE TABLE stock_balance (
    warehouse_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity DECIMAL(18, 3) NOT NULL,
    PRIMARY KEY (warehouse_id, product_id)
);
```

Целевая таблица PostgreSQL:

```sql
CREATE TABLE stock_balance (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    warehouse_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity NUMERIC(18, 3) NOT NULL,
    CONSTRAINT uq_stock_balance_business_key
        UNIQUE (warehouse_id, product_id)
);
```

Прежний составной ключ становится бизнес-ключом, новый `id` — идентификатором Entity. Не следует автоматически удалять старые колонки.

## 4. Переписывание зависимых FK

Источник:

```sql
CREATE TABLE stock_reservation (
    id BIGINT PRIMARY KEY,
    warehouse_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity DECIMAL(18, 3) NOT NULL,
    FOREIGN KEY (warehouse_id, product_id)
        REFERENCES stock_balance (warehouse_id, product_id)
);
```

Целевой вариант:

```sql
CREATE TABLE stock_reservation (
    id BIGINT PRIMARY KEY,
    stock_balance_id BIGINT NOT NULL,
    warehouse_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity NUMERIC(18, 3) NOT NULL,
    CONSTRAINT fk_reservation_balance
        FOREIGN KEY (stock_balance_id) REFERENCES stock_balance(id)
);
```

Мигратор формирует соответствие `(warehouse_id, product_id) → new_id`, затем подставляет `new_id` в зависимые строки. В MVP старые колонки сохраняются также в зависимых финальных таблицах. Их удаление возможно только как отдельное последующее изменение схемы. Исходные значения сначала загружаются в staging; промежуточные структуры создаются внутри транзакции переноса.

Отдельная mapping-таблица не обязательна: загруженная `stock_balance` с `id` и `UNIQUE(warehouse_id, product_id)` сама задаёт соответствие. Если для staging нужна отдельная карта, в MVP она существует только внутри транзакции. Пример:

```sql
CREATE TEMP TABLE _modernorm_stock_balance_map (
    warehouse_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    new_id BIGINT NOT NULL UNIQUE,
    PRIMARY KEY (warehouse_id, product_id)
) ON COMMIT DROP;
```

Пример обновления уже загруженной промежуточной таблицы, в которой присутствуют обе старые колонки и новая колонка `stock_balance_id`:

```sql
UPDATE _modernorm_stock_reservation_staging AS r
SET stock_balance_id = m.new_id
FROM _modernorm_stock_balance_map AS m
WHERE r.warehouse_id = m.warehouse_id
  AND r.product_id = m.product_id;
```

**Важно:** операции выполняются над staging в целевой БД, где уже присутствуют исходные значения ключевых колонок. После remap данные вставляются в заранее подготовленные финальные таблицы с действующими ограничениями. Mapping и staging не являются checkpoints; после rollback они не используются для возобновления.

## 5. Архитектура

### 5.1. Schema Inspector

Считывает метаданные MySQL: таблицы, колонки, PK, UNIQUE, FK, индексы, типы и ограничения. Выявляет composite PK и все объявленные входящие ссылки, включая неподдерживаемые ссылки на альтернативные составные `UNIQUE`. Неподдерживаемые зависимости блокируют MVP, а не игнорируются.

### 5.2. Schema Transformer

Создаёт детерминированный структурный план: колонки новых ID, сохраняемые бизнес-ключи, staging, необходимые карты ID, преобразования FK и порядок проверок. Конкретные значения новых ID не фиксируются планом. DDL финальной схемы готовится отдельно оператором; автоматическая генерация артефакта DDL остаётся будущим расширением. Команда переноса проверяет готовую финальную схему; `dry-run` не выполняет DDL/DML.

### 5.3. Data Migrator

Реализует отдельный путь загрузки: исходные данные → staging → назначение ID → remap FK → финальные таблицы → проверка. Все изменения цели выполняются в одной транзакции. Используются ограниченные батчи и SQL JOIN вместо хранения всех соответствий в PHP-памяти. В MVP нет checkpoints и промежуточных commits.

Режим `modernorm:data:transfer --schema-rekey` самостоятельно выполняет полный перенос из MySQL, включая staging, новые ID, remap, загрузку и проверку. Он не использует результаты обычного переноса и не выполняет его loader. Текущие `Planner`/`Loader` из `DataTransfer` не расширяются режимом rekey. Правила исправления значений (`trim`, `replace`, `null_to`) не назначают PK/FK; rekey переиспользует существующие `TransformationRules`, `RuleSuggestions`, `SuggestionWizard`, `TransformationJournal`, `TransformationLog` и value validation через адаптер `RekeyRules`. Правила применяются только к обычным полям, а все PK/FK/UNIQUE бизнес-ключи и новые ID защищены. Хеш правил входит в сохранённый план; raw staging сохраняет исходные значения, typed staging и финальная проверка учитывают правила. Границы переиспользования определены в разделе 14.7.

### 5.4. Integrity Validator

Проверяет количество строк, уникальность старых ключей, полноту ID mapping, отсутствие неразрешённых FK, равенство исходных и целевых бизнес-ключей и корректность ссылок. Проверяет соответствие «исходная строка → новый ID → зависимые строки» и двустороннюю сверку ключей. Полная проверка обязательна в MVP; сравнение только `COUNT(*)` недостаточно.

## 6. Политики обработки таблиц

| Политика | Поведение | Применение |
|---|---|---|
| `surrogate` | Новый одиночный PK; старые колонки и `UNIQUE` сохраняются | Таблицы Entity |
| `preserve` | Исходный составной PK сохраняется | В MVP — обычные ManyToMany join tables; произвольные таблицы вне runtime ORM — будущее расширение |
| `skip` | Явное исключение таблицы с проверкой замкнутости зависимостей | Будущее расширение; MVP не пропускает неподдерживаемые таблицы |

**ManyToMany:** обычные join tables могут сохранять составной физический PK без Entity. Их перенос выполняется отдельно от преобразования PK Entity. Переназначение FK join tables на преобразуемые Entity входит в MVP в пределах поддерживаемого ациклического графа. План явно задаёт исходные колонки, новые FK и целевой PK пары; старые колонки сохраняются для проверки. Если на переписываемую пару ссылаются другие таблицы, MVP блокирует такой случай. Уже существующая поддержка прямого переноса обычных join tables сама по себе remap не выполняет.

## 7. CLI и предварительный план

`modernorm:data:transfer --schema-rekey` — отдельный сценарий полного переноса внутри общей команды. CLI, правила, генератор предложений и журнал общие; планировщик, staging, allocator, remapper и orchestration отдельные. Самостоятельная команда `modernorm:schema:rekey` не регистрируется.

```bash
# Анализ MySQL и проверка готовой схемы PostgreSQL
php bin/console modernorm:data:transfer \
  --schema-rekey \
  --source-url-env=MYSQL_DATABASE_URL \
  --target-url-env=POSTGRES_DATABASE_URL \
  --dry-run

# Явное сохранение машинно-читаемого плана в новый файл
php bin/console modernorm:data:transfer \
  --schema-rekey \
  --source-url-env=MYSQL_DATABASE_URL \
  --target-url-env=POSTGRES_DATABASE_URL \
  --dry-run --plan-output=rekey-plan.yaml

# Проверочный перенос
php bin/console modernorm:data:transfer \
  --schema-rekey \
  --plan=rekey-plan.yaml \
  --rehearsal

# Выполнение
php bin/console modernorm:data:transfer \
  --schema-rekey \
  --plan=rekey-plan.yaml \
  --execute
```

Опции `--rules`, `--suggest-rules`, `--rules-output`, `--validate-data`, `--change-log`, `--max-error-examples` и `--max-change-examples` переиспользуют обычный механизм переноса. Генератор разрешён только при интерактивном text dry-run без change-log; после сохранения правил сканирование повторяется. Существующий `--plan` может служить исходным проверенным планом; выбранные правила меняют его хеш, а обновлённый план сохраняется только через явный `--plan-output` в новый файл. Для write-режимов передаётся соответствующий `--rules` файл; payload правил в YAML не включается. `--batch-size` ограничивает чтение, не размер транзакции и не назначение ID; он не входит в хеш плана.

Ровно один из режимов `--dry-run`, `--rehearsal`, `--execute` обязателен. `--plan` и `--plan-output` необязательны во всех режимах. Без `--plan` имена переменных окружения задаются явно, план строится в памяти и проверяется перед переносом; с `--plan` имена берутся из файла, а его актуальность перепроверяется. Файл не содержит URL или паролей. Режим rehearsal требует отдельной БД, отличной от application DB; execute разрешает явно выбранную application DB. Для разных целей создаются отдельные планы, endpoint нельзя незаметно переопределить при выполнении.

`--dry-run` читает каталоги и проверяет готовую цель, не выполняет DDL/DML и не обещает полного сканирования значений. Запись файла плана разрешена только через `--plan-output`, существующий файл не перезаписывается. Неподдерживаемые случаи выводятся как blockers; план с blockers нельзя выполнить. Resume отсутствует.

Отчёт включает преобразуемые таблицы, зависимые FK, колонки, ограничения, индексы, порядок загрузки и проверки, требования source fence и offline. Показывается `data_scanned`; точное количество строк без отдельного сканирования не заявляется. Резервная копия и maintenance mode остаются обязанностью оператора.

## 8. Последовательность MVP

1. **Discovery / Plan:** прочитать схему, построить граф, явно описать преобразования таблиц и FK; вывести `dry-run` и блокирующие случаи.
2. **Target schema:** отдельно проверить и применить DDL финальных таблиц, ограничений и индексов; адаптировать ORM mapping. Таблицы должны быть пустыми.
3. **Offline / Fence:** остановить запись приложения и обращения к цели; установить обязательный source fence до snapshot, проверить права и отсутствие timeout.
4. **Preflight:** под удерживаемым fence открыть read-only InnoDB snapshot; повторно проверить схему, типы, имена, поддерживаемые зависимости и соответствие плану.
5. **Begin target:** начать одну транзакцию PostgreSQL, заблокировать финальные таблицы от конкурирующей записи и повторно проверить пустоту.
6. **Staging / Copy:** создать транзакционные staging-структуры и загрузить исходные строки ограниченными батчами. Эти структуры не предназначены для runtime ORM.
7. **Remap / Load:** назначить surrogate ID и загрузить родителей; через карты или бизнес-ключи заполнить новые FK в staging и загрузить зависимые финальные таблицы в порядке графа.
8. **Validate:** проверить значения, ограничения, counts, полное соответствие ключей и связей; принудительно проверить отложенные ограничения. Финальные UNIQUE/FK действуют при загрузке, их отключение не предусматривается.
9. **Commit:** удалить служебные staging-структуры внутри той же транзакции либо использовать временные структуры с `ON COMMIT DROP`; зафиксировать только проверенный результат.
10. **Release / Cutover:** после определённого результата commit освободить source fence; оператор сохраняет запрет записи и вручную переключает приложение после подтверждённого commit и проверки работоспособности. Запись в источник остаётся остановленной до завершения переключения.

Команда не делает финальную синхронизацию после snapshot и не удаляет старые бизнес-колонки. Их возможное удаление — отдельное последующее изменение схемы.

## 9. Безопасность и восстановление

- Копирование использует read-only snapshot; write-режим дополнительно удерживает source fence без изменения исходных данных. `dry-run` не выполняет DDL/DML и не устанавливает глобальную блокировку.
- Цель заранее подготовлена и пуста. Ошибки FK, дубликаты, коллизии бизнес-ключей и неоднозначные преобразования останавливают перенос.
- При ошибке до commit выполняется rollback всех транзакционных изменений цели, включая staging и mapping. Повторный запуск требует пустых финальных таблиц и заново выполняет весь перенос; автоматического продолжения нет.
- При потере соединения во время COMMIT результат может быть неопределённым (`target_data_committed: null`). Автоматический повтор запрещён до проверки фактического состояния цели оператором.
- Новые ID могут отличаться между неуспешными попытками. Непрерывность ID не гарантируется: PostgreSQL sequences могут продвинуться даже после rollback.
- Внешние действия триггеров не откатываются вместе с БД. Rehearsal требует изоляции таких действий, как и существующий перенос.
- Журнал диагностики может пережить rollback, но не является checkpoint или доказательством commit. Постоянный mapping для resume в MVP не создаётся.
- До cutover приложение может вернуться к неизменённому источнику. После начала записи в PostgreSQL обратная синхронизация требует отдельного решения.
- Future resumable требует самостоятельного контракта атомарности checkpoints, стабильности ID и согласования с состоянием источника. Его гарантии не распространяются на MVP.

## 10. Enterprise-риски

- Неявные связи без объявленных FK не могут быть надёжно переписаны автоматически.
- Внешние приложения и отчёты могут зависеть от прежнего составного ключа.
- Циклические FK требуют особого порядка загрузки или отложенного создания ограничений.
- Ссылки на составные `UNIQUE`, nullable-колонки и различия семантики `NULL` требуют отдельной проверки.
- Коллации, регистр символов и сравнение строк в MySQL и PostgreSQL могут различаться.
- Составные индексы, нужные для бизнес-запросов, нельзя удалять только потому, что PK стал одиночным.
- Физическая миграция данных не обновляет ORM mapping и SQL-код автоматически.

## 11. Этапы реализации

| Этап | Содержание | Приоритет |
|---|---|---|
| MVP | Inspector, явный структурный план, `dry-run`, блокировка неподдерживаемых случаев | Обязательно |
| MVP | Проверка заранее подготовленной цели; `BIGINT`, сохранение бизнес-ключей | Обязательно |
| MVP | Staging, назначение ID и remap объявленных FK, включая поддерживаемые ManyToMany | Обязательно |

| Future / resumable | Отдельный resumable-контракт: checkpoints, постоянные карты ID, согласованность источника, потенциально CDC | Отдельное проектирование |
| Future / extensions | UUID, сложные зависимости, дополнительные политики таблиц и автоматизация адаптации | Позже |

## 12. Критерии приёмки MVP

- Таблица с `(a, b)` PK переносится с новым `BIGINT id` PK, исходными `NOT NULL` колонками и `UNIQUE(a, b)`.
- Source fence получен до snapshot и удерживается до результата commit/rollback; отсутствие необходимых прав, timeout и потеря соединения блокируют перенос. Данные MySQL не изменяются.
- Финальная схема подготовлена заранее; несоответствие плану или непустая цель блокируют перенос.
- Staging, mapping, remap и финальная загрузка выполняются без промежуточных commits в одной транзакции PostgreSQL.
- Все исходные строки присутствуют без потерь и дублей; проверено полное соответствие бизнес-ключей новым ID.
- Поддерживаемые объявленные FK и ManyToMany ссылаются на правильные новые ID; проверяется соответствие исходных и целевых связей, а не только отсутствие FK-ошибок.
- Проверки выявляют отсутствующие, лишние и неверно связанные записи и блокируют commit.
- Циклы, ссылки на альтернативные составные UNIQUE, nullable составные FK и неподдерживаемые цепочки преобразований явно блокируются до загрузки.
- Ошибка до commit приводит к rollback транзакционных изменений; повторный запуск с чистой целью выполняется с начала. Сохранение выданных в неуспешной попытке ID не требуется.
- Неопределённый исход commit явно диагностируется и требует проверки цели до повторного запуска.
- Источник не изменяется; старые ключевые колонки автоматически не удаляются. При завершении staging и временные карты удалены.
- После ручной адаптации mapping и cutover Entity использует одиночный PK без composite PK runtime. Автоматическая адаптация приложения не заявляется.

Обязательные негативные сценарии реализации: конкурентная запись заблокирована fence; отсутствие прав/timeout/потеря исходного соединения не дают успешного переноса; изменение target fingerprint блокирует загрузку; неверный remap на существующий чужой ID выявляется; подмена неключевого значения выявляется при равных counts; blocked edge и цикл блокируют весь план; unsupported key type отклоняется до загрузки; rollback и неопределённый commit корректно различаются. Обычный `modernorm:data:transfer` проверяется отдельными regression-тестами без изменения его контракта.


## 13. Архитектурное решение

**Рекомендация:** не усложнять Identity Map, Unit of Work и Hydrator ModernORM исключительно ради legacy composite PK. Реализовать отдельный namespace `ModernORM\Bundle\SchemaRekey` за флагом `modernorm:data:transfer --schema-rekey`. Режим выполняет полный перенос с преобразованием ключей и не является постобработкой обычного переноса. MVP реализует только offline transactional; resumable остаётся отдельным будущим контрактом.

При этом поддержка composite PK в runtime остаётся независимой возможностью, которую можно реализовать позднее, если продукт должен работать непосредственно с существующими схемами без их изменения.

## 14. Обязательные технические контракты

### Приоритеты

| Приоритет | Проблема | Обязательный результат |
|---|---|---|
| P0 | Неизменность источника | Source fence до snapshot и до завершения целевой транзакции |
| P0 | Целевая схема и staging | Проверяемые проекции, типы, ограничения и жизненный цикл |
| P0 | Соответствие данных | Формальные проверки строк, ID и рёбер связей |
| P0 | Граф FK | Полный учёт зависимостей и fail-closed для неподдерживаемых случаев |
| P1 | Семантика MySQL | Точное представление значений и блокировка неоднозначных сравнений |

| P1 | Граница DataTransfer | Отдельная orchestration без изменения обычного переноса |
| P2 | Формат плана | Версионируемый YAML с fingerprint и строгой валидацией |

P0/P1 входят в MVP. Базовый формат P2 также нужен для `--plan`; расширения формата не должны задерживать формализацию P0.

### 14.1. Неизменность источника (P0)

В MVP write-режимы используют один обязательный механизм: `FLUSH TABLES WITH READ LOCK` на исходном MySQL-соединении **до** открытия read-only REPEATABLE READ snapshot. Это глобальная блокировка всего MySQL instance, а не только выбранной БД. Она требует `FLUSH_TABLES` или `RELOAD`; выделенный SELECT-only пользователь без этих прав для write-режимов недостаточен. Данные источника команда не изменяет. Семантика блокировки и прав описана в [MySQL 8.4 FLUSH Statement](https://dev.mysql.com/doc/refman/8.4/en/flush.html).

Соединение с блокировкой и snapshot одно и то же: автоматический reconnect запрещён. План фиксирует `source_fence: mysql_global_read_lock` и конечный timeout ожидания; отсутствие прав или timeout прерывают работу до записи в цель. Исходная БД должна состоять из поддерживаемых InnoDB-таблиц; системные и log tables исключаются из допустимого source database.

Сразу после получения fence заново инвентаризируются таблицы и FK, сверяются fingerprints и открывается snapshot. Блокировка удерживается во время копирования, всех проверок и до получения результата commit/rollback. Перед commit проверяются то же исходное соединение и сохранённый session ID без reconnect; потеря соединения до commit вызывает rollback цели. Смена/освобождение fence во время переноса недопустимы. При потере связи с источником во время целевого COMMIT успешная offline-гарантия не заявляется: отчёт отдельно фиксирует состояние fence и известный/неопределённый результат PostgreSQL.

`COUNT(*)`, повторное чтение того же snapshot, timestamps и fingerprint схемы не доказывают отсутствия новых изменений; они не заменяют fence. Между MySQL и PostgreSQL нет общей атомарной транзакции. После освобождения fence команда не гарантирует неизменность источника: запрет записи до cutover поддерживает оператор. Если глобальная блокировка недопустима, MVP останавливается; альтернативный проверяемый fence требует отдельного расширения контракта, а не обходного флага.

`dry-run` не удерживает fence: его план — структурный снимок, который write-режим обязан перепроверить. Для rehearsal также требуется fence, чтобы проверять тот же алгоритм консистентности.

### 14.2. Готовая цель и staging (P0)

План задаёт для каждой таблицы исходное имя, целевое schema-qualified имя, упорядоченную проекцию колонок, source PK, target PK, бизнес-ключ, конверсии, сохраняемые колонки и remap. Полное source inventory должно быть покрыто планом. Обычные таблицы с одиночным PK переносятся с сохранением ID; составные Entity PK преобразуются; join tables имеют собственную явно описанную проекцию.

До загрузки проверяются типы и precision/scale, signedness/range, nullability, defaults, generated/identity columns, PK/UNIQUE/FK с порядком колонок, referenced schema/table/columns, MATCH и действия ON UPDATE/DELETE. Для изменённых FK целевое действие явно задано и проверено; автоматическое сохранение поведения MySQL не предполагается. Все ограничения должны быть включены и валидны. Неуказанные исходные колонки и обязательные целевые колонки без значения блокируют план. MVP допускает дополнительные целевые колонки только для новых ID и FK; поддержка default/generated projections остаётся будущим расширением.

После блокировки всех финальных таблиц в детерминированном порядке повторяются fingerprint и проверка пустоты. RLS, inheritance/partitioning и пользовательские триггеры на финальных таблицах в MVP rekey блокируются; внутренние FK-триггеры разрешены. Это намеренно более строгий контракт, чем обычный DataTransfer.

`StagingManager` создаёт только TEMP-таблицы с `ON COMMIT DROP` внутри целевой транзакции. Имена генерируются командой и не принимаются как SQL из плана. Staging не копирует defaults, identity, бизнес-триггеры и FK финальных таблиц. Он содержит:

- точное представление source PK и всех переносимых исходных значений;
- служебный ordinal строки для диагностики, не заменяющий source PK;
- отдельные типизированные колонки целевых значений;
- `new_id` и результирующие FK, заполняемые allocator/remapper.

Raw-представление сохраняется отдельно от target casts: байты и длины для строк/binary, точный decimal text для чисел, отдельный признак NULL. Нельзя сначала привести ключ к потенциально суженному типу и использовать результат как исходную идентичность. Временная карта, если нужна, имеет UNIQUE на полном исходном ключе и UNIQUE на новом ID. Финальные бизнес-ограничения действуют при INSERT; промежуточные nullable FK допустимы только в staging.

### 14.3. Формальный алгоритм валидации (P0)

Обозначения: `S(T)` — строки source snapshot; `E(T)` — ожидаемая целевая проекция из staging; `F(T)` — финальная таблица; `M(T)` — соответствие полного исходного PK новому ID. Для preserve `M` сохраняет идентификатор. Составной ключ — упорядоченный кортеж типизированных компонентов; конкатенация с разделителем запрещена.

Проверки обязательны для каждого запуска и выполняются до commit:

1. **Source → staging:** повторно прочитать `S(T)` ограниченными keyset-батчами в том же snapshot; для каждого полного PK найти ровно одну raw staging-строку и побайтно сверить канонические исходные значения. Проверить равенство counts и отсутствие staging PK вне source. Первое и повторное чтение не заменяют source fence.
2. **Mapping:** каждый source PK имеет ровно один `new_id`; каждый `new_id` соответствует ровно одному source PK. Проверить оба anti-join направления, уникальность и полноту. Нулевое число несовпадений обязательно.
3. **Expected projection:** построить `E(T)` только из проверенных source-значений и `M`. Для каждого remapped FK `(child PK, old parent PK)` вычислить единственный ожидаемый parent ID. Отсутствие или несколько родителей — ошибка; строки не пропускаются.
4. **Staging → final:** проверить counts и оба anti-join направления по ожидаемому target PK. По каждой найденной строке сравнить **все** проецируемые значения с `E(T)` через null-safe сравнение. Текст/binary сверяются по точному представлению; числа и даты — по явно объявленной канонизации без округления. Дополнительные default/generated projections не входят в MVP и блокируются.
5. **Edges:** для каждой исходной связи проверить, что финальная child-строка ссылается именно на `M(parent source PK)`, а не просто на существующий ID. Для ManyToMany сравнить полное множество ожидаемых пар в обе стороны и отсутствие дублей. Сохранённые старые FK-колонки также сверяются с source.
6. **Constraints:** выполнить `SET CONSTRAINTS ALL IMMEDIATE`, проверить завершённость всех таблиц/рёбер и нулевые mismatch counters. Только затем разрешить commit.

Проверка не ограничивается sample, counts или совпадением хешей. Хеши допустимы как ускорение, но не заменяют точное сравнение. SQL JOIN/anti-join выполняются в PostgreSQL; повторное source-чтение ограничено батчем. Отчёт включает counts по таблицам и связям, coverage каждой проверки, bounded примеры без значений данных и итог `validation_complete`.

### 14.4. Граф зависимостей (P0)

Inspector инвентаризирует все обычные таблицы и объявленные FK выбранной MySQL database независимо от ORM mapping. Вершина графа — физическая таблица; ребро — FK с упорядоченными local/referenced columns, referenced key и действиями. Все source tables должны иметь политику; внешние входящие FK из других доступных схем также проверяются через каталог. Невозможность полной инвентаризации зависимостей из-за прав блокирует выполнение.

Каждое ребро получает ровно один статус: `preserve`, `remap` или `blocked`. Неизвестные рёбра и неподдерживаемые типы не отбрасываются. Проверяются:

- обе вершины и все колонки присутствуют в плане; ссылки за пределы выбранной БД блокируются в обоих направлениях;
- remap ссылается на полный исходный PK родителя, nullable composite FK и ссылки на альтернативные UNIQUE блокируются;
- переписываемый FK не входит в идентификатор зависимой Entity или ключ с входящими ссылками;
- join table без входящих ссылок допускается как исключение: переписывается полный target PK пары;
- self-reference и все strongly connected components с циклом блокируются, даже если constraints deferrable;
- после классификации строится топологический порядок и замыкание зависимостей преобразуемых таблиц.

Один blocked edge блокирует **весь план**, а не только отдельную таблицу или её загрузку. В отчёте указываются constraint, обе вершины, причина и путь от преобразуемой таблицы. Запрещены частичный remap, silent skip и ручное удаление blocker из YAML без повторного анализа каталогов.

### 14.5. Семантика исходных значений (P1)

MySQL session фиксирует и сообщает charset/collation, `sql_mode` и timezone. Числа выше PHP_INT_MAX и DECIMAL читаются/передаются как точные строки; float не используется для ключей или decimal-конверсий. Запрещены truncation, округление, замена invalid dates и неявная timezone-конверсия. UTF-8/NUL, диапазоны и precision проверяются до финального INSERT. NULL не равен пустой строке или нулю.

Для MVP компоненты **преобразуемых PK и remapped FK** ограничены целочисленными MySQL-типами с lossless целевой проекцией. Signed/unsigned учитываются отдельно; unsigned BIGINT не обязан помещаться в BIGINT PostgreSQL, поэтому старый бизнес-ключ может потребовать NUMERIC(20,0), явно заданный планом. Это не меняет тип нового surrogate ID.

Текстовые, binary, temporal и decimal компоненты преобразуемых ключей блокируются до появления отдельного контракта эквивалентности. В частности, нельзя переносить MySQL case-insensitive/PAD SPACE сравнение в PostgreSQL через обычный `=` или `trim`. Остальные переносимые значения поддерживаются только при явной точной конверсии; коллизия целевого UNIQUE блокирует commit. Расширение допустимых ключевых типов — отдельная задача, не неявный fallback.

### 14.6. Стратегия BIGINT ID (P1)

MVP использует положительные signed BIGINT: `1..9223372036854775807`. Для каждой surrogate-таблицы `SurrogateIdAllocator` назначает `1..N` в лексикографическом порядке **исходного PK по типам MySQL**. Для integer компонентов сравнение точное с учётом signed/unsigned, без сортировки decimal text и преобразования в PHP float. `N` и предел диапазона проверяются до загрузки финальной таблицы.

ID выделяются один раз в staging; remap и финальный INSERT используют эту же карту. Во время копирования identity/default не назначает ID повторно: вставляются явные значения, при необходимости с `OVERRIDING SYSTEM VALUE`. Обычные preserve-таблицы сохраняют свои PK и не участвуют в allocator.

Одинаковый snapshot и план дают одинаковые ID; между разными попытками это не публичная гарантия, поскольку источник мог измениться. Новая ID-колонка цели должна быть BIGINT identity с принадлежащей sequence, start/minvalue 1, increment 1, NO CYCLE и совместимым диапазоном. Перед commit проверяются sequence settings/capacity; после полной валидации sequence синхронизируется с максимальным назначенным ID, для пустой таблицы — с её start без `is_called`. Ошибка синхронизации блокирует commit; продвижение sequence не откатывается и не является признаком успешного переноса.


Namespace: `ModernORM\Bundle\SchemaRekey`.

| Компонент | Ответственность |
|---|---|
| `RekeyTransfer` | CLI, чтение строгого плана, source fence/snapshot, target transaction, guards, orchestration стадий, отчёт и решение commit/rollback |
| `RekeyPlanner` | Детерминированный структурный план, fingerprints, политики и проекции; не назначает ID и не пишет в БД |
| `SchemaInspector` | Независимое от runtime mapping чтение MySQL/PostgreSQL каталогов, полный inventory и проверка готовой цели |
| `DependencyGraph` | Классификация всех FK, SCC/замыкания, blockers и топологический порядок |
| `StagingManager` | TEMP DDL, bounded copy, raw/typed projections и cleanup внутри транзакции |
| `SurrogateIdAllocator` | Назначение BIGINT, построение и проверка карт, подготовка sequence sync |
| `ForeignKeyRemapper` | Точный remap объявленных FK/ManyToMany через проверенные карты, проверка единственности matches |
| `RekeyValidator` | Source/staging/final сверка строк, mapping и edges, coverage и mismatch report; не выполняет commit |

`RekeyTransfer` выполняет финальные INSERT из проверенных staging projections по плану; изменение обычного `DataTransfer\Loader` для этого не требуется. По мере реализации внутренние вспомогательные классы допустимы, но граница namespace и перечисленные ответственности сохраняются.

Разрешено переиспользовать низкоуровневые connection guards, описание target types, scalar value validation и безопасное quoting/binding, только если их контракт совпадает. Текущий `DataTransfer\Planner`, batch-reader с одинаковой source/target проекцией, правила PK/FK и `Loader::load()` не используются как rekey orchestration. Существующий `TransferCommand` направляет rekey-выполнение в `RekeyTransfer`; existing CLI, JSON-report и поведение `modernorm:data:transfer` остаются совместимыми. При реализации обязательны regression-тесты обычного переноса и отдельные rekey integration tests на PHP 8.6.

### 14.8. Машинно-читаемый план (P2)

План — декларативный YAML, `version: 1`, без SQL, исполняемых выражений, custom YAML tags, aliases, secrets и checkpoints. Неизвестные поля, дубли ключей YAML/таблиц/рёбер и неподдерживаемая версия отвергаются. Скалярные идентификаторы/значения, где важна точность, задаются строками. Ниже каркас, не полный исполняемый план:

```yaml
version: 1
command: modernorm:data:transfer
schema_rekey: true
rules: {hash: '<rules-sha256>', rules: []}
execution: offline_transactional
connections:
  source_url_env: MYSQL_DATABASE_URL
  target_url_env: POSTGRES_DATABASE_URL
source_fence:
  strategy: mysql_global_read_lock
  timeout_seconds: 30
id_strategy:
  type: bigint
  allocation: source_pk_order
endpoint_identity:
  source: {instance: '<source-instance-id>', database: '<source-db>'}
  target: {instance: '<target-instance-id>', database: '<target-db>'}
fingerprints:
  source_schema: '<sha256>'
  target_schema: '<sha256>'
tables: []       # полный inventory, политики, PK, проекции, бизнес-ключи
foreign_keys: [] # все рёбра и preserve/remap/blocked, local/referenced columns
load_order: []
blockers: []
plan_hash: '<sha256>'
```

Полные записи `tables` обязательны: source database/table и target schema/table, policy (`preserve`/`surrogate`), kind (`entity`/`join_table`), source/target PK, business key, новые ID/FK колонки, ordered column projections с source/target type и conversion code, null/default/generated contracts, constraints/indexes. FK-запись содержит обе вершины, порядок колонок, referenced key, nullable/MATCH/actions, classification, результирующий FK и причину blocker. Порядок загрузки всегда пересчитывается по графу.

Schema fingerprint — SHA-256 канонического каталога по отсортированным physical identifiers и структурным свойствам: source engine, columns/types/collations, PK/UNIQUE/FK/indexes; target columns, defaults/generated/identity/sequence settings, constraints/indexes, RLS/partitioning/triggers. Текущие sequence values, row counts и данные в schema fingerprint не входят. Endpoint identity (source instance/database, target instance/database) сохраняется в плане отдельно от credentials и перепроверяется при выполнении; изменение environment variable не должно перенаправлять план на другую цель без ошибки.

`plan_hash` вычисляется по каноническому JSON разобранного плана, исключая само поле hash; UTF-8, порядок полей канонический, порядок семантически упорядоченных массивов сохраняется. Это проверка целостности, не подпись или разрешение на выполнение. Write-режим перепроверяет весь план по реальным каталогам под source fence и target locks; совпадения одного hash недостаточно. Отредактированный план должен пройти все структурные проверки и получить новый hash через повторное планирование.

Отчёт выполнения содержит `command`, `plan_hash`, mode, stage, source-fence outcome, `data_scanned`, `validation_complete`, counters, blockers/failure и `target_data_committed` (`false`/`true`/`null`). Exit code 0 означает структурный dry-run без blockers либо подтверждённый commit полностью проверенного переноса; 1 — blockers/validation/load failure; ошибка COMMIT с неизвестным исходом также возвращает ненулевой код.
